# 线上文章集体 404 排查记：EdgeOne 路由器的点号陷阱与 slug 去点迁移

2026-11-19 晚，我随手点开自己博客的一篇文章，404。换一篇，还是 404。**所有文章页都是 404**——而首页、归档、统计页全都好好的，首页上明明就列着这些文章的链接。最终的凶手小到可笑：URL 路径段里的**两个点号**。本文记录从「全站文章阵亡」到「slug 去点自救上线」的全过程，给同样症状的后来者留一张排查地图。

本文写给两类读者：

- **想复现或自救的访客**：文末「排查清单」与「复刻清单」按步骤列出，症状吻合即可对号入座；
- **未来的维护者（包括新会话的 AI 助手）**：读完应知道为什么本站 slug 从此不许带点、旧链接为什么救不回来、以及平台工单提了什么。

---

## 〇、现象：好得诡异，死得整齐

故障面非常「挑食」：

| 请求 | 结果 |
|---|---|
| `/` 首页（含文章列表） | 200 |
| `/archive/` `/about/` `/tags/` `/categories/` 等静态页 | 200 |
| `/fcircle/` `/analytics/` `/rss.xml` | 200 |
| `/posts/任意文章/` | **404** |

首页列着链接、点进去就是 404——这个组合排除了「整站挂了」「DNS 挂了」「部署没跑」一大片嫌疑，也把问题精确定位在**文章页这一层**。

---

## 一、排查：层层剥洋葱（含两次虚惊）

### 1.1 先怀疑构建/部署把产物弄丢了

第一反应是最近的部署出了幺蛾子。于是取证：

1. **本地跑一遍 `astro build`**：67 个页面全部生成，`dist/posts/` 下 33 个文章目录整整齐齐——代码和构建管线无罪；
2. **看线上 `sitemap-0.xml`**：里面赫然列着 33 个 `/posts/` 链接。sitemap 是构建完成后才产出的清单，**它在，就说明平台侧构建确实生成了这些页面**；
3. **`/pagefind/pagefind.js` 可访问**：说明完整构建链（含 pagefind 索引）都跑完了。

三件套一摆，「构建没生成」的假设也死了。剩下的可能只有两种：部署同步时丢了文件，或者 URL 解析出了问题。

### 1.2 虚惊一场的两个方向

排查路上有两个岔路口白跑了几步，记录下来免得后人重蹈：

- **「部署丢了整个 posts 目录」**——一度最像的答案。推翻它的证据是：`/posts/azuma.zuomu-blog-23/index.html` **直接访问是 200**，816KB 的全文好端端躺在对象存储里。目录 URL 404、直接文件 URL 200，丢文件论不攻自破；
- **「标签页/分类页也全灭了」**——实测 `/tags/运维/` 确实 404，一度以为损坏面更大。结果本地构建产物里**本来就没有**这类页面（67 页的构成里没有独立标签页），404 是正常行为，虚惊一场。

顺带解开的一个谜团：某些请求会返回跳转到 `/fireflypriweb-xxxxxxxxxxxx/原路径` 的 302。那串后缀每次部署都不同——它是**部署 ID**，属于平台「未命中就导去部署命名空间」的怪癖，跳转目标同样 404，与本案无关，纯红鲱鱼。

### 1.3 致命对照实验

真正的破案点是一组只差一个变量的对照：

| 请求 | 结果 |
|---|---|
| `/posts/web-update-1/`（路径段**不带点**） | **200** |
| `/posts/azuma.zuomu-blog-1/`（路径段**带点**） | **404** |
| `/posts/azuma.zuomu-blog-1/index.html`（直接指文件） | **200** |

同一个父目录、同样的深度、同样的请求姿势，唯一区别就是 `azuma.zuomu-blog-1` 里那两个点。再用随机查询参数做缓存穿透复测，结果一致——**不是边缘缓存的陈年毒药，是路由器当场就解析不了**。

### 1.4 根因

结论：**EdgeOne Pages 的路由器把「带点号的路径段」当成了带扩展名的文件名**。请求 `/posts/azuma.zuomu-blog-1/` 时，它去找字面对象 `posts/azuma.zuomu-blog-1`（把 `.zuomu-blog-1` 当扩展名），找不到就 404，**根本不会回退到 `index.html` 默认文档**；而 `web-update-1`、`about`、`firefly` 这类不带点的路径段则老实走默认文档解析。文章对象从头到尾都在，死的只是「目录式 URL → index.html」这一步。

---

## 二、「以前怎么没事」的真相

这是排查中最扎心的一问。答案是：**「以前」是 Cloudflare 的以前**。

带点的 slug（`azuma.zuomu-blog-N`）从 9 月起就有，那时站点跑在 Cloudflare Pages 上，CF 的静态路由没这个毛病。**10 月 17 日整站迁移到 EdgeOne Pages**，换了路由器，这颗雷就埋下了——从那一刻起，带点 slug 的文章页 URL 其实已经全部 404。

那为什么一个月没人发现？三个巧合叠在一起：

1. **验证习惯**：日常视觉/交互验证都在本地 dev server 上看效果，线上文章页极少点开；
2. **404 页伪装得太好**：本站 404 页是主题渲染的，皮肤跟正常页面几乎一样，扫一眼还以为文章搬了家；
3. **外围全绿**：首页、归档、RSS、友圈都是好的，只有「点进文章」这一步才踩雷。

不是平台一夜变坏，是雷埋了一个月才被踩响——这大概是最有教育意义的一点：**迁移换宿主，必须拿真实 URL 做端到端回归，别只看首页**。

---

## 三、修复：slug 去点迁移

平台的 bug 短期指望不上（工单见第五节），自救方案只有一个：**把 slug 里的点去掉**。

### 3.1 方案取舍

| 方案 | 结论 |
|---|---|
| **slug 去点**（`azuma.zuomu-blog-N` → `azuma-zuomu-blog-N`） | **采用**：改动确定、立即生效、无平台依赖 |
| 平台 URL 重写规则 | 优先级最高的治本方案，但当前部署形态下无此配置入口 |
| 提工单等平台修 | 同步进行，治本 |

旧 URL 的取舍值得一说：`/posts/azuma.zuomu-blog-N/` 这批链接本来就**全部 404**（从 10-17 起就死了），所以改 slug 不存在「牺牲还能用的链接」的问题；而路由器的病连重定向桩都发不出来（重定向页同样住在带点路径下，一样解析不到），旧链接只能永久躺平。损失可接受：sitemap 会让搜索引擎重新收录，RSS 与友圈聚合也会自动跟上新链接。

### 3.2 改动清单

全量替换 `azuma.zuomu-blog` → `azuma-zuomu-blog`，共 **30 个文件、35 处**：

1. 25 篇文章的 frontmatter `slug` 字段（`txt/` 下 1–25 全量）；
2. 文章内互链（如 20文章 里的三处引用、本文之外的教程互链）；
3. 更新公告与项目页里的绝对链接引用；
4. 一处代码注释（`content-utils.ts` 里举例用的 slug 形态说明）。

两个技术确认点：

- **wiki 链接不受影响**：站内 `[[12文章]]` 式链接由 `remark-wiki-link` 在构建期按 frontmatter 查表生成 URL，slug 改了它自动跟上，零手动改动；
- **排序逻辑不受影响**：`content-utils.ts` 的同天序号逻辑从 id 提取尾部数字，`azuma-zuomu-blog-16` 与 `azuma-zuomu-blog-16`（去点后）都命中同一正则。

### 3.3 验收

- `pnpm check`：0 errors / 0 warnings / 0 hints；
- 本地构建 67 页全生成，`dist/posts/azuma-zuomu-blog-1/` 就位、旧点点路径绝迹；
- 上线后实测 `/posts/azuma-zuomu-blog-25/`、`-1/`、`-12/` 全部 200；
- 友圈数据源（Friend-Circle-Lite 每日爬取）已换血为新链接，旧链接归零。

## 四、踩坑表

| 坑 | 症状 | 处置 |
|---|---|---|
| EO 路由器点号坑 | 目录 URL 404、`index.html` 直访 200 | slug 去点；本质是平台默认文档解析缺陷 |
| 部署 ID 302 | 部分未命中路径 302 到 `/fireflypriweb-<id>/...`，后缀每次部署都变 | 平台未命中回退行为，红鲱鱼，别追 |
| 「标签/分类页也挂了」误判 | `/tags/运维/` 404 | 该类页面本就不生成，先对账构建产物再定损坏面 |
| 「部署丢目录」误判 | 线上整目录 404 | 先直访 `index.html` 验证对象在不在，再谈部署问题 |
| 404 页伪装 | 404 页带主题皮肤 | 排查时先看 HTTP 状态码，别用眼睛判断死活 |
| 迁移回归盲区 | 换宿主后只验证首页 | 端到端回归必须包含真实文章 URL、RSS、404 路径 |

---

## 五、平台工单要点

已向腾讯云提交工单（摘录），期望平台修复默认文档回退逻辑：

- **现象**：路径段含点号的目录 URL 不回退 `index.html`；不含点号的正常；
- **复现**：部署含 `posts/hello.world/index.html` 与 `posts/plain-dir/index.html` 的静态站，前者目录 URL 404、后者 200，直访两者的 `index.html` 均 200；
- **期望**：目录式 URL 与路径段是否含点无关地回退 `<path>/index.html`（主流静态托管均如此）；
- **附带缺陷**：未命中路径的 302 跳转目标（部署命名空间）同样 404，疑似回退逻辑不正确。

---

## 六、给同病者的排查清单

如果你的静态站也出现「首页好、文章全 404」，按这个顺序走：

1. **本地构建**看产物里页面在不在——在，就排除代码问题；
2. **线上 sitemap** 看链接列没列——列了，就排除「构建没生成」；
3. **直访 `index.html`**——200 说明对象在，是 URL 解析问题；404 才是真丢文件；
4. **拿同目录下带点/不带点的两个路径段做对照**——一锤定音；
5. **带随机参数复测**——排除边缘缓存；
6. 命中点号坑就去点（或找平台要 URL 重写/修 bug），没命中就按「部署同步」方向继续查。

---

## 七、经验总结

1. **状态码不会撒谎，页面长相会**：404 页再漂亮也是 404，排查第一步永远是拿 HTTP 状态码画损坏地图；
2. **对照实验是排查的核武器**：一次只变一个变量（点号），比读十页文档都管用；
3. **迁移换宿主是一次「路由器赌博」**：不同平台的 URL 解析细节（尾斜杠、默认文档、点号、大小写）各不相同，迁移后的端到端回归必须覆盖真实 URL 形态；
4. **slug 设计要对基础设施友好**：点号在路径里是「扩展名」的强信号，任何一环把它当文件名都会出事。本站从今往后 slug 只用小写字母、数字与连字符；
5. **自救与治本并行**：去点是止血，工单是根治。止血要快，根治要留痕。
