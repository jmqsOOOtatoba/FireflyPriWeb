# 友圈停更 27 天排查记：GitHub fork 用量拦截与爬虫自托管迁移

2026-11-19，本站友圈（Friend-Circle-Lite）恢复更新：数据生成从 GitHub Actions 挪到**自有备案服务器**上按日爬取，推送链路（`page` 分支 → Vercel → `fc.mstzuomu.space`）原封不动，博客端零改动。起因是一次静默停更——页面上「更新时间」焊死在 `2026-10-23 07:26:38` 整整 27 天，朋友们 10 月底、11 月的新文章一篇都不出现，而数据链每一环单看都健康。真凶藏在 GitHub 的一层强制拦截里。

本文写给两类读者：

- **想复现的访客**：文末「复刻清单」从零列出全部步骤，deploy.sh 与 crontab 可照抄，不依赖本站任何私有环境；
- **未来的维护者（包括新会话的 AI 助手）**：读完应知道链路每一段在哪、哪些「绿灯」是假象、服务器侧的目录与密钥布局、以及为什么从此不需要点 GitHub 的 Enable workflows。

---

## 〇、现象：更新时间永远停在那一刻

友圈页面（`/fcircle/`）本身完全正常：样式正常、加载正常、旧文章列表正常，唯独「更新时间」不再前进。第一反应是爬虫挂了或者数据站被墙了，但随手一查就发现——这个时间戳本身就是最好的线索。

---

## 一、排查：从时间戳倒推到 run #98

先摆出友圈的三段式数据链（详细设计见[友圈部署教程](/posts/azuma-zuomu-blog-12/)）：

```
博客 public/friend.json（友链名单）
   │   ▼
数据生成：爬虫抓各站 RSS，产出 all.json / link.json / errors.json
   │   强推 page 分支
   ▼
数据托管：Vercel（fc.mstzuomu.space，生产分支 = page）
   │   前端 fetch all.json
   ▼
博客 /fcircle/ 页面（fclite 前端，自托管在 public/fclite/）
```

`all.json` 里的 `statistical_data.last_updated_time` 就是爬虫写入数据那一刻的北京时间。于是按链路逐段验证：

| 验证点 | 位置 | 结果 | 判定 |
|---|---|---|---|
| 数据站存活 | `curl -sI https://fc.mstzuomu.space/all.json` | 200 + `Access-Control-Allow-Origin: *` | 正常 |
| 数据新鲜度 | `all.json` 的 `last_updated_time` | `2026-10-23 07:26:38` | 停更 |
| `page` 分支最后提交 | GitHub API `commits?sha=page` | `github-actions[bot]`，`2026-10-22T23:26:39Z` | 与上行对得上 |
| Actions 运行记录 | GitHub API `actions/runs` | 最新 run #98，`2026-10-22T23:26:02Z` 起跑、success | 对得上 |
| 10-23 之后的 run | `actions/runs?created=>2026-10-23` | **0 条** | 调度断供 |

时间戳严丝合缝：run #98 在 **UTC 2026-10-22 23:26** 执行（换算北京时间正是 10 月 23 日 07:26），爬虫把 `last_updated_time` 写进 `all.json` 并强推 `page` 分支，Vercel 部署完成——那就是页面显示的「更新时间」。此后 GitHub 没有再派发过任何一次定时任务。

顺带一提，run 的间隔在断供前就已经不对劲：`22 */4 * * *` 的 cron 本该每 4 小时一跑，最后几天的实际间隔却漂到了最长近 9 小时。这算是不祥之兆。

**小结：不是爬虫挂了，不是 Vercel 挂了，是调度源头被掐断了。**

---

## 二、假象与死路：API 里全是绿灯

按常规剧本，调度断供 = workflow 被禁用了。但 API 返回的信息全是绿的：

- `GET /actions/workflows/367575528` → `state: "active"`
- `GET /actions/permissions` → `{"enabled": true, "allowed_actions": "all"}`
- 仓库未归档、未被停用；账号也活着——同账号另一个仓库的 CI 在 11 月 17 日还在正常跑

真正暴露问题的是手动触发：

```
POST /actions/workflows/367575528/dispatches
→ 422 {"message": "Actions has been disabled for this repository."}
```

**「Actions has been disabled」——而上面两个接口都说它开着。** 换言之，workflow 的 `state` 与仓库的 `permissions.enabled` 只是用户设置层，拦在它们之上的还有一层 GitHub 的强制状态，REST API 既读不到也改不动。

抱着「说不定能踢一脚」的心态，把能试的 API 都试了一遍：

| 操作 | API | 结果 |
|---|---|---|
| workflow 关了再开（踢调度器） | `PUT .../workflows/{id}/disable` → `enable` | 均 204，dispatch 仍 422 |
| 仓库级开关 false→true 翻转 | `PUT .../actions/permissions` | 204，dispatch 仍 422 |
| 两个 workflow 都 enable | `PUT .../workflows/{id}/enable` ×2 | 204，无变化 |
| 换 ref 手动触发 | `dispatches`，ref=main / ref=page | 均 422 |
| 找「enable」专用端点 | `/actions/enable` 等 | 404，不存在 |

死路。这层拦截不在 REST API 的管辖范围内。

---

## 三、真凶：横幅上写得明明白白

用浏览器打开仓库的 Actions 页，横幅赫然写着：

> **Workflows are not currently being run on this fork due to the scale of GitHub Actions usage. A repository maintainer can choose to re-enable these.**

GitHub 嫌这个 fork 的 Actions 用量太大，把整个 fork 的工作流运行停了。要点有三：

1. **fork 专属待遇**：同账号的非 fork 仓库一切正常，这个 fork 全灭；
2. **「用量」看的是生态而不是你**：Friend-Circle-Lite 上游有一批 fork 在跑同款定时爬虫，GitHub 对这类 fork 网络的整体用量下手；本地这个 fork 一天 6 次、每次一分钟的用量本身微不足道；
3. **重启用是网页端 maintainer 的事**：横幅明说 "A repository maintainer can choose to re-enable these"，API 通道并不存在。

于是问题变成一道选择题。

---

## 四、方案决策：不点 Enable，直接搬家

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 点 Enable workflows | 网页端恢复，继续用 Actions cron | 随时可能再被掐；且 cron 对低活跃仓库本就拖沓（断供前已如上述） |
| **B. 搬到自有服务器**（采用） | 服务器 cron 跑爬虫，强推 `page` 分支 | 需要一台常驻机器——而备案服务器本来就是 24 小时开机 |
| C. 服务器直接托管数据 | nginx 直接吐 `all.json`，弃用 `page` 分支 | 动 DNS、动 `fcircleConfig.apiUrl`、重建 CORS，改动面大 |

选 B 的决定性理由：**整条发布链路一根手指都不用动**。`page` 分支依旧是 Vercel 的发布源，域名、CORS、博客前端配置全部保持原样，只是把「谁来跑爬虫」从 GitHub Actions 换成了自己人。哪天连 GitHub 的 git 托管都不想要了，再考虑 C 不迟。

顺带把频率从「每天 6 次」降到**每天 1 次（下午 4 点）**：友圈不是新闻流，一天刷一次足够新鲜，流量也省一个数量级（见 §6.3）。

## 五、部署实录

### 5.1 目标架构

```
备案服务器（图床同机，2 GB 轻量，北京）
   │  crontab 0 16 * * *（Asia/Shanghai）
   ▼
/home/ubuntu/fcl/deploy.sh
   ├─ venv 里的 run.py 抓 RSS → all.json / link.json / errors.json
   ├─ 拷贝发布布局：main/ + 8 个静态文件 + 3 个 JSON
   └─ 临时 git init → 强推 page 分支
   │
   ▼
GitHub（jmqsOOOtatoba/Friend-Circle-Lite，推送凭据 = repo 级部署密钥）
   │  page 分支变更触发
   ▼
Vercel 自动部署 → fc.mstzuomu.space/all.json
   │
   ▼
博客 /fcircle/ 前端拉取（与原先完全一致）
```

### 5.2 推送凭据：部署密钥，不用个人 PAT

服务器要往 GitHub 推 `page` 分支，凭据用**仓库级部署密钥**：

```bash
# 服务器上生成
ssh-keygen -t ed25519 -f ~/.ssh/fcl_deploy -N "" -C "fcl-crawler-deploy"

# ~/.ssh/config 追加
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/fcl_deploy
    IdentitiesOnly yes
    StrictHostKeyChecking accept-new
```

公钥挂到仓库的 Settings → Deploy keys（勾选 Allow write access），或用 API `POST /repos/{owner}/{repo}/keys`（`read_only: false`）。两条原则：

1. **权限最小化**：部署密钥只对这一个仓库有效，随时可一键吊销；
2. **不放个人 PAT**：个人 token 泄露波及整个账号，部署密钥泄露只波及单个仓库。

验证：`ssh -T git@github.com` 应返回 `Hi <owner>/<repo>! You've successfully authenticated...`（部署密钥认证显示的是仓库名而不是用户名，这是正常的）。

### 5.3 目录布局

```
/home/ubuntu/fcl/
├── repo/        # fork 仓库克隆（run.py、conf.yaml、static/ 都在这）
├── venv/        # Python 虚拟环境
├── build/       # 每次发布前重建的静态产物暂存区
├── logs/cron.log
├── deploy.sh    # 一次完整的「爬取 → 发布」
└── run-once.sh  # 手动触发入口（nohup 后台跑）
```

### 5.4 deploy.sh（可照抄）

```bash
#!/usr/bin/env bash
set -euo pipefail
export TZ=Asia/Shanghai

REPO_DIR="$HOME/fcl/repo"
VENV="$HOME/fcl/venv"
BUILD_DIR="$HOME/fcl/build"
PUSH_URL="git@github.com:jmqsOOOtatoba/Friend-Circle-Lite.git"

echo "===== $(date '+%F %T') FCL run start ====="
cd "$REPO_DIR"

# venv 缺失/残废时整个删掉重建
if [ ! -f "$VENV/bin/activate" ]; then
    rm -rf "$VENV"
    python3 -m venv "$VENV"
    "$VENV/bin/pip" install -q -r "$REPO_DIR/requirements.txt"
fi
source "$VENV/bin/activate"

python run.py

# 发布布局与线上 page 分支一致：main/ + 8 个静态文件 + 3 个 JSON
rm -rf "$BUILD_DIR"
mkdir -p "$BUILD_DIR"
cp -r main \
    static/edgeone.json static/_headers static/vercel.json static/index.html \
    static/readme.md static/favicon.ico static/bg-light.webp static/bg-dark.webp \
    all.json link.json errors.json "$BUILD_DIR/"

cd "$BUILD_DIR"
git init -q
git config user.name "fc-crawler"
git config user.email "fc-crawler@users.noreply.github.com"
git add -A
git commit -q -m "⏱️ $(date '+%Y年%m月%d日-%H时%M分') 服务器定时更新"
git push -q --force "$PUSH_URL" HEAD:page
echo "===== $(date '+%F %T') pushed to page branch ====="
```

三个实现要点：

1. **发布布局必须与线上 `page` 分支对齐**：`main/`（fclite 前端的 js/css）+ 8 个静态文件 + 3 个 JSON。照仓库自带 `deploy.sh` 那样 `cp -r main static ...` 也能跑，但会把文档截图一并带进 `page` 分支——站点里多一堆没人要的 png；
2. **强推 orphan 提交**（在 `build/` 里临时 `git init`）：与原 Actions workflow 的发布方式等价，`page` 分支永远只有一条「定时更新」提交，不留历史包袱；
3. **venv 自愈条件要看 `bin/activate` 而不是 `bin/python`**（坑见 §6.2）。

### 5.5 定时任务

```text
MAILTO=""
0 16 * * * /bin/bash /home/ubuntu/fcl/deploy.sh >> /home/ubuntu/fcl/logs/cron.log 2>&1
```

服务器时区本来就是 `Asia/Shanghai`，`0 16 * * *` 即每天下午 4 点。手动补跑与盯进度：

```bash
bash ~/fcl/run-once.sh     # 后台执行，日志进 logs/cron.log
tail -f ~/fcl/logs/cron.log
```

## 六、验收与踩坑

### 6.1 首跑验收

2026-11-19 18:34 手动触发首跑，约 3 分半后推送成功、Vercel 自动部署完成：

| 指标 | 结果 |
|---|---|
| 友链总数 | 21 个 |
| 成功出文章的站点 | 17 个（不可达 1 个） |
| 文章总数 | **84 篇**（停更时 74 篇，停更期间的新文章全部补上） |
| `all.json` 的 `last_updated_time` | `2026-11-19 18:37:33` |

验证时注意 fclite 前端有 **10 分钟 localStorage 缓存**，要看最新数据请开无痕窗口，别对着旧缓存误判「没修好」。

### 6.2 踩坑表

| 坑 | 症状 | 处置 |
|---|---|---|
| API 假象 | workflow `state: active`、`permissions.enabled: true`，但 dispatch 422「Actions has been disabled」 | 这两处只是用户设置层；判定 Actions 生死以 dispatch 响应码与网页横幅为准 |
| 停用拦截 API 无解 | disable/enable、开关翻转、双 workflow enable 全试过，dispatch 依旧 422 | 这层状态没有 REST 通道；要么网页端点 maintainer 按钮，要么弃用 Actions |
| venv 半成品 | `python3 -m venv` 因 ensurepip 缺失报错后留下残废目录；此后按 `bin/python` 判存在性会误判，`source activate` 直接炸 | Ubuntu 先 `apt install python3.14-venv`（版本随 Python 走）；自愈检查看 `venv/bin/activate`，残废目录 `rm -rf` 重建 |
| 发布布局跑偏 | 照上游 `cp -r static`，文档截图进了 `page` 分支 | 显式拷 8 个静态文件，与原 Actions 产物对齐 |
| 时区对账 | 页面「更新时间」是北京时间，GitHub 页面/接口是 UTC | `2026-10-23 07:26:38`（北京）= run #98 的 `2026-10-22T23:26Z`；对账先统一时区 |

### 6.3 流量账（搬服务器前先算过）

爬虫的流量大头在输入侧的 RSS 全量下载——实测 21 个友链的 feed：

- **解压后共约 9.1 MB/轮**，其中三个「全文输出」大户占七成（1.6 MB / 1.2 MB / 1.0 MB，各家把全文塞进了 RSS）；
- XML 的 gzip 压缩比实测约 **15%**（样本区间 11%–32%），`requests` 默认收压缩体，实际过网约 **1.5–2 MB/轮**；
- Friend-Circle-Lite **没有条件请求缓存**（每次全量重拉，SQLite 只缓存 feed 地址与文章追踪），这笔开销每轮固定。

按每天 1 次的现行频率约 **60–80 MB/月**；就算加回当年的每天 6 次也才 300–400 MB/月，对一台月流量包以 GB 计的轻量服务器来说是零头。

## 七、复刻清单

1. **前置**：一台常驻 Linux 服务器；Python 3.10+；fork 好 Friend-Circle-Lite，且 `conf.yaml` 的 `json_url` 已指向自己站点的 `friend.json`（漏改会去爬上游作者的几百个陌生友链，这是真实事故）；
2. **部署密钥**：服务器生成 `~/.ssh/fcl_deploy`，公钥挂到 fork 仓库 Settings → Deploy keys（Allow write access），`~/.ssh/config` 指定 IdentityFile；`ssh -T git@github.com` 通过；
3. **代码与环境**：`git clone git@github.com:<owner>/<repo>.git ~/fcl/repo`；Ubuntu 先 `apt install python3.14-venv`；`python3 -m venv ~/fcl/venv && ~/fcl/venv/bin/pip install -r ~/fcl/repo/requirements.txt`；
4. **脚本就位**：照 §5.4 写 `~/fcl/deploy.sh`（改 `PUSH_URL`）与 `~/fcl/run-once.sh`，`chmod +x`；
5. **手动跑一发**：`bash ~/fcl/run-once.sh`，盯 `logs/cron.log` 直到 `pushed to page branch`；
6. **验收**：`curl -s https://<数据站>/all.json` 里 `last_updated_time` 应为刚才的北京时间；网页端无痕窗口查看；
7. **上定时器**：crontab 加 `MAILTO=""` 与 `0 16 * * *`（频率自定）；
8. **收尾**：GitHub 侧的 Actions 不用管了，旧 workflow 里的 secrets 可以删掉；数据站托管在 Vercel 的话什么都不用改。

## 八、经验总结

1. **绿灯会骗人**：`state: active` 与 `permissions.enabled: true` 只表达「用户设置」，不代表「GitHub 允许运行」。判定 Actions 生死，看 dispatch 的响应码和 Actions 页的横幅，别信这两个字段；
2. **时间戳是最好的证人**：数据文件里的一行 `last_updated_time` 直接锁定最后一次成功的运行时刻，比翻日志、猜配置都快。排查停更类问题，先对时间戳再动手；
3. **平台的免费调度随时可以变卦**：GitHub Actions 的 cron 对 fork、对低活跃仓库有各种隐性折扣（延迟、跳过、整体停用）。定时任务真在意准时与可控，放在自己的常驻机器上最踏实；
4. **迁移的最小代价是「只换执行者」**：本次一行博客代码没改、一条 DNS 没动，只换了「谁来跑爬虫」。发布链路保持不变，回滚也只是改回 crontab 的事；
5. **凭据跟着权限最小化走**：服务器上放仓库级部署密钥而不是个人 token，爆炸半径被钉死在单个仓库内。
